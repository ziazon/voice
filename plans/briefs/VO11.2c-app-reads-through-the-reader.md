# VO11.2c brief: the app reads history and the claude.ai export through the reader

VO11.2a landed the reader's sandbox profile and launch as a library (`voice_agent::reader::Reader`,
brief `plans/briefs/VO11.2a-reader-profile.md`). VO11.2b landed the hidden `voice reader <step>`
command and its protocol (`voice_api::reader`, brief `plans/briefs/VO11.2b-reader-in-the-cli.md`).
Today the app still reads the person's history in its own process: `builder/app/src/commands.rs`
calls `voice_api::claude_code_folders`, `read_claude_code`, `use_claudeai_export`,
`claudeai_export_status`, `list_claudeai_chats` and `read_claudeai`, which call the `_in`
functions in `builder/api/src/history.rs` directly. This slice makes those public functions start
the shipped `voice` as the reader, under the profile, with exactly that step's sources, and relay
its answer. Skills (`voice reader skills`) are **not** in this slice (VO11.2d).

## 2. A reader client in the API

New file `builder/api/src/reader_client.rs`, `pub mod reader_client;` in `builder/api/src/lib.rs`
(not re-exported with `*`). It holds:

```rust
/// Where the app's reader runs: the shipped `voice` and the folder for its run folders.
pub struct Place<'a> {
    pub program: &'a Path,
    pub runs: &'a Path,
}
```

and one function per step, each taking the **canonical** home (see § 3), a `&Place`, the request
and, for the two reads, the progress callback:

```rust
pub fn claude_code_folders(home: &Path, place: &Place<'_>, request: SlugRequest) -> Result<ClaudeCodeFolders>
pub fn read_claude_code(home: &Path, place: &Place<'_>, request: ReadRequest, progress: &mut dyn FnMut(ReadProgress)) -> Result<ReadCounts>
pub fn claudeai_export_status(home: &Path, place: &Place<'_>, request: SlugRequest) -> Result<Option<ExportStatus>>
pub fn list_claudeai_chats(home: &Path, place: &Place<'_>, request: SlugRequest) -> Result<ChatList>
pub fn read_claudeai(home: &Path, place: &Place<'_>, request: SlugRequest, progress: &mut dyn FnMut(ReadProgress)) -> Result<ClaudeaiCounts>
pub fn use_claudeai_export(home: &Path, place: &Place<'_>, slug: &str, path: &Path, folder: bool) -> Result<ExportStatus>
```

(`Result` is `std::result::Result<T, Failure>` as in `history.rs`.) Each does, in order:

1. `history::readable(home, slug)` (make it reachable; it is `pub(crate)` already). This gives
   `FIND`, the outside-state message and `PERMISSION` exactly as today, without starting anything.
   The reader checks again inside.
2. Its sources:
   - Claude Code steps: `home.join(".claude/projects")`. If `fs::symlink_metadata` of it is
     `NotFound`, there is nothing to read: return the in-process `history::claude_code_folders_in`
     or `history::read_claude_code_in` answer (it reads no history when the folder is missing, and
     still takes the lock and checks permission). Any other metadata error: the step's own failure
     (`FOLDERS` or `READ`). Otherwise the one source `Source::Folder(&projects)`.
   - claude.ai steps: `history::chosen_export(home, slug)` (make it `pub(crate)`). `None` gives
     `Ok(None)` for the status and `EXPORT_GONE` for the list and the read, as the `_in`
     functions do today; its errors pass through. Otherwise the one source
     `Source::Folder(path)` when the stored `folder` is true, else `Source::File(path)`.
   - `use_claudeai_export`: `history::choose_claudeai_export_in(home, slug, path, folder)` in the
     app's process (it writes only the app's own state file), then `claudeai_export_status` above.
3. The reader: `Reader::new(place.program, home, &member_dir, &state_dir, place.runs, &sources, &deny)`
   where `member_dir` is `assistants::find(home, slug)`'s `dir` (`None` or an error: `FIND`),
   `state_dir` is `member::private_state_dir(&member, home)` (`None`: the outside-state failure),
   and `deny` is `DenyList::for_member(&member, home)` (error: its text, as `history.rs` does). A
   `Reader::new` error whose text is `voice_agent::text::READER_SOURCE` maps to the step's own
   failure (`FOLDERS`, `READ`, or `EXPORT_BAD` for the claude.ai steps); any other `Reader::new`
   error maps to `reader::STOPPED`.
4. Run it: `reader.command(&["reader", step.name()])` with `stdin(Stdio::piped())`,
   `stdout(Stdio::piped())`, `stderr(Stdio::null())`; spawn (error: `STOPPED`). Write the request
   (`serde_json::to_vec` of the request DTO, which is exactly what the reader parses) to stdin,
   then **drop stdin** so the reader sees the end of input; a write error is not itself a failure
   (the reader may have exited), the judgement below decides. Read stdout through § 2.5, then
   `wait()` the child. If judging stops early (a violation), `kill()` then `wait()` first. The
   child is always waited for; `Reader` is dropped after the wait (its `Drop` removes the run
   folder).
5. **Judge the run by its lines** (a private generic function over `impl BufRead`, so it is unit
   tested without a process):
   - Read one line at a time with a cap: a line (without its `\n`) longer than
     `reader::MAX_LINE + 64` bytes, or more than `reader::MAX_LINE + (1 << 20)` bytes in total
     across all lines, is a violation.
   - Each line must end in `\n` and parse as a JSON object with exactly one key:
     - `progress`: allowed only for `read-claude-code` and `read-claudeai` (else a violation); its
       value must parse as `ReadProgress`; pass it to the callback at once (the relay).
     - `result`: must parse as the step's DTO (`ClaudeCodeFolders`, `ReadCounts`,
       `Option<ExportStatus>`, `ChatList`, `ClaudeaiCounts`); must be the last line.
     - `error`: must be a string of at most 4096 bytes with no control character
       (`char::is_control`); it becomes `Failure { message }`; must be the last line.
     - Anything else, or any line after a `result` or `error`, is a violation.
   - End of output with no `result` or `error` line is a violation (a reader that exits early).
   - After the wait: a `result` counts only with exit status 0, an `error` only with exit status 1;
     any other pairing is a violation.
   - Every violation is the one fixed failure `reader::STOPPED`. Never show the reader's own
     words for a violation.
6. Doc comment on the module: one or two lines saying the app reads history only through its own
   reader, under the profile, and trusts nothing it prints beyond the protocol.

## 3. The public functions use it on macOS

In `builder/api/src/history.rs`, on `#[cfg(target_os = "macos")]` only, the public
`claude_code_folders`, `read_claude_code`, `claudeai_export_status`, `list_claudeai_chats`,
`read_claudeai` and `use_claudeai_export` call the `reader_client` functions with:

- the canonical home: `fs::canonicalize` of the `HOME` that `home()` returns (error: `FIND`), so
  the reader's `HOME` and its profile's paths agree;
- `Place { program: &shipped, runs: &runs }`, where `shipped` is
  `voice_core::cli_command::shipped_cli()` (error: `STOPPED`) and `runs` is
  `voice_agent::claude::profile_folder(&home).parent().unwrap().join("reader-runs")`. Before
  using it, create that parent (`Library/Application Support/Voice`) if missing with
  `fs::DirBuilder::new().recursive(true).mode(0o700)` (error: `STOPPED`); `Reader::new` makes
  `reader-runs` itself. A folder of its own, so a `claude` launch and a reader never share one.

`use_claudeai_export` gains the `folder: bool` argument on every platform. On other platforms the
public functions keep calling the `_in` functions as today (the reader is macOS only).

`builder/app/src/commands.rs`: `choose_claudeai_export` passes `request.folder` to
`voice_api::use_claudeai_export`. Nothing else in the app changes: the reader and a `claude` child
are each started by the app's own process, so they are siblings, never one inside the other.

## 8. The security review's fixes

Sections 1 to 7 are done and committed. This section makes exactly these changes, in
`builder/api/src/reader_client.rs` and the docs, and nothing else. Test first.

### 8.1 Deadlines, so a reader can never hang the app

Today `run` reads stdout until it closes, then waits. A reader that prints nothing and never
exits, or prints its final line and then keeps stdout open, blocks the app's step forever.

1. Split the reading from the judging. A helper thread (`std::thread::spawn`) owns the child's
   stdout and does the bounded reading that `judge` does today (`take(MAX_LINE + 66)` and
   `read_until(b'\n')`, the per-line and total caps), sending each complete line as
   `Vec<u8>` over a `std::sync::mpsc` channel, then one end-of-output message (or one
   over-the-cap / read-error message) and returning. The judging stays on the calling thread
   (the progress callback is not `Send`): a small state struct with a `line(&mut self, &[u8])`
   that applies today's rules per line, and an `end(self)` that gives the final answer. Keep the
   rules and the fixed `STOPPED` sentence exactly as they are.
2. The calling thread receives with `recv_timeout`:
   - before the final line, at most `QUIET` (a `const QUIET: Duration`, 10 minutes) between two
     lines; reads report progress as they go, so a longer silence is a stuck reader;
   - after the final `result` or `error` line, at most `AFTER` (a `const AFTER: Duration`,
     5 seconds) for the end of output.
   A timeout is a violation: `kill()` the child, `wait()` it, and return `STOPPED`. Do not join
   the helper thread after a kill (another process may still hold the pipe; the thread ends when
   the pipe closes). On the normal path, join it.
3. Make the deadlines parameters of a private function that the unit tests call with short
   durations, over any `impl Read + Send + 'static` and a kill callback, so it is tested without
   a process. Unit tests, with `std::io::pipe()` (a writer kept open blocks the read):
   - nothing written and the writer kept open: `STOPPED` after the short quiet deadline, and the
     kill callback ran once;
   - a valid result line written, writer kept open: `STOPPED` after the short after-deadline, the
     kill callback ran once;
   - a valid result line then the writer dropped: the result, the kill callback never ran;
   - progress lines spaced closer than the quiet deadline, for longer than it in total, then a
     result: the result (the deadline is between lines, not for the whole run).

### 8.2 Only Voice's own sentences reach the screen

Today an `error` line's text is shown if it is short and has no control character. Instead, an
`error` line's text is shown only when it equals one of Voice's own fixed sentences that the
five history steps can send: `history::FIND`, `ELSEWHERE`, `PERMISSION`, `BUSY`, `SAVE` (make it
`pub(crate)`), `FOLDERS`, `READ`, `EXPORT_GONE`, `EXPORT_BAD`, `NO_CHATS` (make it `pub(crate)`),
`reader::REQUEST`, `reader::TOO_MUCH` and `reader::STOPPED`. Any other `error` text (with exit
status 1) becomes the step's own sentence (`FOLDERS` for the folders step, `READ` for the Claude
Code read, `EXPORT_BAD` for the claude.ai steps): it is a refusal the reader explained in its own
words, such as a password-file path, which the app no longer shows. Drop the 4096-byte and
control-character checks (the list makes them moot). Update the unit tests: an error with a
control character, one over 4096 bytes, and one with any unlisted text each give the step's
sentence; a listed sentence with exit 1 gives exactly that sentence; a listed sentence with exit
0 is still `STOPPED`.

### 9.2 A deny-listed download is refused when chosen, with its own sentence

member's deny list (`DenyList::for_member(&member, home)`, its error mapped as `read_export` maps
it) and run `deny.check(path)`, plus `deny.check(&path.join("conversations.json"))` when `folder`,

`builder/api/tests/deny_rules.rs::chosen_export_under_ssh_shows_denial_instead_of_export_bad`
expects on the in-process path, and that no choice is saved (status is `None`).

### 9.3 The missing-projects shortcut reads nothing

In `reader_client.rs`, when `~/.claude/projects` is missing, do not call
`claude_code_folders_in` or `read_claude_code_in` (they would mine in the app if the folder
appeared between the two checks). Instead: for the folders step, after `readable`, return
`ClaudeCodeFolders { found: false, folders: vec![] }`; for the read, take
`history::locked(home, &request.slug)?` (make it reachable if needed), then return the same
all-zero `ReadCounts` that `read_claude_code_in` returns for a missing folder. Put that zero value
in one `pub(crate) fn` in `history.rs` used by both places, so they can't drift. The existing
`missing_projects_returns_empty_answers_without_a_run_folder` test keeps passing.

### 9.4 A reader that closes its output but never exits

After the end of output, `run` calls `child.wait()`, which blocks forever if the reader closed
stdout but never exits. Replace it with a bounded wait: poll `child.try_wait()` every 10 ms for at
most `AFTER`; if it hasn't exited, `kill()` then `wait()` and return `STOPPED`. Make the poll a
small private function taking the duration, and unit test it on a real short-lived child
(`/bin/sleep 5` with a 100 ms limit: killed, `STOPPED`, returns well under 5 s; `/usr/bin/true`
with a 5 s limit: its status).

### 9.5 Small

`claudeai_export_status` in `reader_client.rs` reads `chosen_export` twice; read it once and pass
the path and kind on (make `export_step` take them).
