# VO14.3 brief: the permissions and audit-log screens

VO14.1 built read permissions (`voice_agent::grants`: `calendar.read`, a dated window per assistant,
revocable) and their audit log, with the CLI `voice grants show|give|revoke` and `voice audit show`.
VO14.2 built the calendar read from a file the person exported, chosen with `voice calendar choose`.
This slice puts the same things **in the app**, per assistant: each capability with its permission
(on or off, its window, the day it was given), giving it or changing its window, **Turn off**; the
calendar file choice; and the audit log, newest first, in plain lines. The app calls the same library
as the CLI, and the parity test lists the pairs.

Read first: `AGENTS.md`, `.ai/PROJECT.md`, `.ai/SECURITY.md` (the webview row and the two grant and
calendar rows), `CONTRIBUTING.md`, `builder/ui/README.md`, `plans/briefs/VO4.3-skills-screen.md`
(the same shape of slice; follow its patterns wherever this brief is silent), and
`plans/briefs/VO14.1-grants-and-audit-log.md` § 1.
Skills: `~/.codex/skills/tdd-skill/SKILL.md`, `~/.codex/skills/security-and-hardening/SKILL.md`,
`~/.codex/skills/code-quality/SKILL.md`, `~/.codex/skills/frontend/SKILL.md`,
`~/.codex/skills/design-guide/SKILL.md`, `~/.codex/skills/plain-language/SKILL.md` (every sentence
a person reads), `~/.codex/skills/project-config/SKILL.md`.

This is a public repo: invented names only (an assistant "Pebble" with slug `pebble` in Rust tests,

no real person, no fixed paths, no real secret in a fixture. **Commit nothing; leave every change

Out of scope: anything that shows calendar events in the app or sends them to a model (VO14.4, which

## 1. Decisions already made (do not change them)

- **Where it lives:** a new card `Permissions.vue` on the Save step's page, after `Skills` and before
  `Forget` in `VoiceApp.vue` (`:key="`permissions-${assistant.slug}-${resets}`"`). Inside the card,
  at its bottom, a child component `AuditLog.vue` (§ 6.3). No new rail step, so `steps.ts` and the
  rail tests don't change.
- **Giving permission is in the app too**, not only Turn off: the person is in the app, and a grant
  is their own dated consent. Giving again replaces the grant and dates it today (as
  `grants::give` already does), which is how the window is changed.
- **No history consent needed**, as the CLI: permissions, the calendar choice and the log are found
  with `calendar::member_in` (it needs the assistant listed and its private state folder in place,
  never the history permission).
- **Only fixed sentences cross as failures** (`.ai/SECURITY.md`). Every `Err` maps to one of the
  sentences in § 3 or an existing crate const, never an error's own text, never a path, never the
  id the webview sent. A damaged `grants.json` makes `grants::load` return a sentence **with the
  file's path**; it must never reach a `Failure` (§ 3 maps it).
- **Success words come from the shared wording** in `voice_agent::text` (`grant_window`,
  `grant_given`, `grant_revoked`, `audit_entry`, `typed_name`), so the app and the CLI say the same
  thing. They carry the assistant's name (the name the person typed) and the calendar file's name
  (cleaned by `typed_name`), as data shown only as text.
- **Command names** (appended, in this order, at the end of every list in § 5):
  `list_permissions`, `give_permission`, `turn_off_permission`, `choose_calendar_export`,
  `audit_log`.

## 2. Two honest fixes in existing code (`builder/api/src/calendar.rs`)

1. **`BAD_GRANTS` gives advice that can't work.** It says "Give permission again", but `grants::give`
   refuses on a damaged file. New text, exactly:
   `Voice's permissions file for this assistant is damaged, so it read nothing. To see where it is, run voice grants show in a terminal, delete it, then give permission again.`
   (`voice grants show` prints the damaged file's path to the person's own terminal.) Update the
   tests that pin it.
2. **`read_calendar_through` can put a path in a `Failure`.** It maps any `Error::Invalid(text)`
   from `grants::require` to `failure(&text)`, and for a damaged file that text is
   `text::grants_damaged(path)`. New mapping: `Invalid(t)` where `t == text::no_grant(Capability::CalendarRead)`
   → `failure(&t)`; any other `Invalid(_)` → `failure(BAD_GRANTS)`; anything else → `failure(LOG)`
   (as today). Add a test in `builder/api/src/calendar/tests.rs`: a damaged `grants.json`
   (e.g. `{"version":2,"grants":[]}`, 0600) and a chosen export → `read_calendar_through` fails with
   exactly `BAD_GRANTS`, the message doesn't contain the temp home's path, and the audit log gained
   one `refused` line with reason `damaged`.

## 3. The api (`builder/api/src/permissions.rs`, new; `pub mod permissions; pub use permissions::*;` in `lib.rs`)

Each command has `foo_in(home: &Path, request) -> Result<Dto>` and `foo(request)` (home from
`assistants::home`), as the other api modules. Every request DTO has `#[serde(deny_unknown_fields)]`;
every DTO derives as the others in `dto.rs` and is `#[ts(export)]`, `rename_all = "camelCase"`.

**DTOs (in `builder/api/src/dto.rs`):**

```rust
pub struct Permission {
    pub id: String,              // capability.id(), e.g. "calendar.read"
    pub words: String,           // capability.words(), e.g. "read your calendar"
    pub on: bool,
    pub given_on: Option<String>,// the grant's day, only when on
    pub past_days: u16,          // the grant's window when on, else Window::DEFAULT's
    pub next_days: u16,
    pub window: Option<String>,  // text::grant_window(grant.window), only when on
}
pub struct Permissions {
    pub permissions: Vec<Permission>,     // one per Capability::ALL, in that order
    pub calendar: Option<CalendarExport>, // the chosen export, name through text::typed_name
}
pub struct PermissionsChanged { pub permissions: Permissions, pub said: String }
pub struct GivePermissionRequest { pub slug: String, pub id: String, pub past_days: u16, pub next_days: u16 }
pub struct PermissionRequest { pub slug: String, pub id: String }
pub struct ChooseCalendarRequest { pub slug: String, pub folder: bool }
pub struct AuditRequest { pub slug: String, pub last: u32 }
pub struct AuditLog { pub lines: Vec<String>, pub unreadable: u32, pub older: bool }
```

**Commands:**

- `list_permissions(SlugRequest) -> Permissions`: `member_in`; `grants::load` (no lock, as the CLI's
  `show`); a row per `Capability::ALL`; `calendar` from `calendar_export_in`, its `name` passed
  through `text::typed_name`. With no state folder yet, `grants::load` answers no grants (a missing
  folder reads as no file), so every row is off and nothing is created; test 1 covers it.
- `give_permission(GivePermissionRequest) -> PermissionsChanged`: `member_in`;
  `Capability::from_id(&id)` else `UNKNOWN`; `Window::new(past_days, next_days)` else
  `text::WINDOW_RANGE`; the lock exactly as the CLI's (`private::lock_existing_state`, NotFound →
  `text::NO_STATE_FOR_GRANTS`, `private::BUSY` → `history::BUSY`, anything else →
  `PERMISSION_SAVE`); under the lock, `grants::load` first and any `Err` → `DAMAGED`; then
  `grants::give(.., SystemTime::now())`: `Err(Invalid(t))` with `t == text::GRANT_NOT_LOGGED` →
  that sentence, any other `Err` → `PERMISSION_SAVE`. `said` is `text::grant_given(&member.name, &grant)`;
  `permissions` the fresh list.
- `turn_off_permission(PermissionRequest) -> PermissionsChanged`: as give for the member, the id,
  the lock and the damaged check; `grants::revoke`: any `Err` → `PERMISSION_SAVE`. `said` is
  `text::grant_revoked(&member.name, capability, changed)`.
- `check_calendar_choice(SlugRequest) -> ()` (for the app to call **before** opening the file
  window, so a refusal doesn't come after the person picked a file): `member_in`; if
  `home/.claude/state/<slug>` doesn't exist (`symlink_metadata` NotFound) → `calendar::NO_STATE`.
- `use_calendar_export_in(home, slug, path) -> CalendarExport`: `calendar::choose_calendar_export_in`
  (its failures already are fixed sentences), with the name through `text::typed_name`. The public
  `use_calendar_export(slug: &str, path: &Path)` takes home from `assistants::home`. It is the only
  api call that takes a path, and only the app's own Rust (the native file window) gives it one.
- `audit_log(AuditRequest) -> AuditLog`: `member_in`; `last` 1–1,000 else `text::AUDIT_LAST`;
  `grants::audit(home, slug, last)` → `Err` → `AUDIT_READ`; `lines` are `text::audit_entry` of each
  entry, newest first as returned; `unreadable` saturates at `u32::MAX`.

**Fixed sentences** (consts in `permissions.rs`; add each to the reader client's known list in
`builder/api/src/reader_client.rs` only if it can come back from the reader — none of these do, so
don't):

| Const | Sentence | When |
| --- | --- | --- |
| `UNKNOWN` | `Voice can't be given that permission.` | an id `Capability::from_id` doesn't know |
| `DAMAGED` | `Voice's permissions file for this assistant is damaged, so it reads nothing that needs your permission. To see where it is, run voice grants show in a terminal, delete it, then give permission again.` | `grants::load` fails, in any command |
| `PERMISSION_SAVE` | `Voice couldn't save this. Check there's space on this computer, then try again.` | as above |
| `AUDIT_READ` | `Voice couldn't read this assistant's log. Try again.` | `grants::audit` fails |

`list_permissions` with a damaged file returns `Err(failure(DAMAGED))`.

### 6.2 `src/screens/Permissions.vue` (export it from `src/index.ts`)

`defineProps<{ assistant: Assistant }>()`, mirroring `Skills.vue`: a `<section class="card mt-4"><div class="card-body p-5">`,
`loading` / `loadError` with a **Try again** button, `busy` disabling every button and input while
any call runs, `message` (`alert-success`) and `error` (`alert-warning`, `role="alert"`), every
failure through `failureMessage(failure, <fallback>)`. All text through `{{ }}` only. Words in a new
`src/screens/permissions/words.ts` (as `skills/words.ts`).

- Title `What your assistant may read`. Under it: `Voice reads a source only when you give it
  permission here, only for the days you allow, and writes each read in the log below. You can turn
  a permission off at any time.`
- Loading: the spinner pattern with `Looking at this assistant's permissions…`. Load fallback:
  `Voice couldn't look at this assistant's permissions. Try again.`
- One block per permission row (a `div` with a top border between rows, as the design guide's
  quiet list; no table). The heading is the words with a capital first letter (`Read your
  calendar`), with a badge after it: `On` (`badge bg-green-lt`) or `Off` (`badge bg-secondary-lt`).
- When on: `From <given_on>: <window>.` (e.g. `From 2026-11-02: from today to 14 days ahead.`).
- Two number inputs, labelled with `<label for>`: `Days back` (`min 0`, `max 31`) and `Days ahead`
  (`min 1`, `max 92`), prefilled from the row's `pastDays` / `nextDays`, each with a small muted
  hint: `0 to 31` / `1 to 92`.
- Buttons: when off, `Give permission` (`btn btn-primary`); when on, `Change the window`
  (`btn btn-outline-primary`) and `Turn off` (`btn btn-outline-danger`). Accessible names include
  the words: `aria-label="Give permission to read your calendar"`, `"Change the window to read your
  calendar"`, `"Turn off permission to read your calendar"`. Give and Change call
  `givePermission({ slug, id, pastDays, nextDays })` with the inputs' values as integers; Turn off
  calls `turnOffPermission({ slug, id })`.
- On success: the rows are replaced by `permissions`, `message` is `said`. On failure: `error`
  (fallback `Voice couldn't save this. Try again.`), **and the list is loaded again** so what's
  shown is what's in place (a failed give or revoke may or may not have changed the file).
- Under the calendar row only (`id === 'calendar.read'`): the calendar file line,
  `Your calendar file: <name>` (`folder: false`), `Your calendar folder: <name>` (`folder: true`),
  or `No calendar file chosen yet. Export your calendar as an .ics file, then choose it here.`;
  buttons `Choose a file` and `Choose a folder` (`btn btn-outline-secondary btn-sm`) →
  `chooseCalendarExport({ slug, folder })`. A `null` answer (the window was closed) changes
  nothing and shows nothing. A result replaces `calendar` and shows `message`
  `Voice will read your calendar from <name>.` Fallback `Voice couldn't use that calendar. Try again.`
- After every give, change, turn off or choose, success or failure, bump a counter that keys the
  `AuditLog` child so the log reloads.

## 10. The review's fix (V1, 2026-11-03)

**A moved or damaged calendar choice must not break the card.** `list_permissions_in` takes
`calendar::calendar_export_in(..)?`, so when the chosen file was moved or deleted (`calendar::GONE`)
or `calendar-export.json` is damaged (`calendar::BAD`), the whole list fails: the screen shows only
the load error and never the **Choose a file** buttons that would fix it, and a give or turn off
that succeeded reports a failure because its fresh list fails.

- `Permissions` gains `pub calendar_problem: Option<String>` (ts `calendarProblem: string | null`).
  When `calendar_export_in` returns `Err(f)` and `f.message` is exactly `calendar::GONE` or
  `calendar::BAD`: `calendar: None`, `calendar_problem: Some(f.message)`. Any other `Err` still
  fails the list. Otherwise `calendar_problem: None`.
- The screen: when `calendarProblem` is set, the calendar line is that sentence (a paragraph with
  `text-warning`) instead of the no-file line; the two choose buttons stay. A successful choose
  clears `calendarProblem`.
- Red first: in `builder/api/tests/permissions.rs`, choose `team.ics`, delete it, then
  `list_permissions_in` is `Ok` with `calendar: None` and `calendar_problem == Some(GONE)`, and
  `give_permission_in` then succeeds with its `said`; a `calendar-export.json` holding `{}` (0600)
  gives `Some(BAD)`. In `Permissions.test.ts`: a `calendarProblem` shows its sentence and both choose
  buttons, and a successful choose removes it. Update every existing `Permissions` value in the
  tests and `fakeBackend` for the new field.
- Then § 9's commands. Commit nothing.
