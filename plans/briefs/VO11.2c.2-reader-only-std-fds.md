## The problem, verified in the toolchain source (Rust 1.98)

- `std/src/sys/pipe/unix.rs` line 34: on macOS a pipe is made with `libc::pipe` and close-on-exec
  is set afterwards, in a second call. A `Command::spawn` on another thread between those two
  calls hands that pipe to its child.
- `std/src/sys/process/unix/unix.rs`: the `posix_spawn` path never sets
  `POSIX_SPAWN_CLOEXEC_DEFAULT`, so every descriptor the app holds without close-on-exec (one
  caught in that window, or one a framework opened without the flag) reaches the reader.

Two effects: the reader can reach another child's pipe (the exposure), and a reader holding a
sibling's pipe keeps that sibling's output open. The reverse also holds and this slice can't fix it:
a child the app starts with `std::process::Command` (the `claude` launch) at the same moment as a
reader can inherit the reader's stdout, so the app sees the reader's answer but the output stays
open, and after 5 seconds the run is `STOPPED` though the answer was right.

## 1. `voice_agent::spawn`: a child that gets only fds 0 to 2

New file `builder/agent/src/spawn.rs`, `pub mod spawn;` in `builder/agent/src/lib.rs`, compiled on
every Unix (the crate builds on Linux today; keep it so).

```rust
pub struct Spawned { pid: libc::pid_t, reaped: bool, pub stdin: Option<File>, pub stdout: Option<File> }
pub fn spawn(program: &Path, args: &[OsString], env: &[(OsString, OsString)], dir: &Path) -> io::Result<Spawned>
impl Spawned {
    pub fn id(&self) -> u32;
    pub fn kill(&mut self) -> io::Result<()>;          // SIGKILL; Ok(()) without signalling once reaped
    pub fn try_wait(&mut self) -> io::Result<Option<ExitStatus>>; // waitpid WNOHANG
    pub fn wait(&mut self) -> io::Result<ExitStatus>;  // waitpid, retried on EINTR
}
impl Drop for Spawned // if not reaped: SIGKILL, then a blocking waitpid (retry on EINTR)
```

- `args` is argv after argv[0]; argv[0] is `program`. `env` is the whole environment: nothing of
  the app's own is added. `dir` is the child's working folder.
- On macOS, in this order:
  1. Two pipes with `libc::pipe`, each end set close-on-exec with `fcntl(F_SETFD, FD_CLOEXEC)` at
     once, every end held as an `OwnedFd` so every error path closes it. If a child-side end (stdin's
     read end, stdout's write end) is 0, 1 or 2, replace it with `fcntl(fd, F_DUPFD_CLOEXEC, 3)`
     and close the original: a dup2 onto itself would otherwise be a no-op the child keeps.
  2. `posix_spawnattr_t` with flags `POSIX_SPAWN_CLOEXEC_DEFAULT | POSIX_SPAWN_SETSIGMASK |
     POSIX_SPAWN_SETSIGDEF`, an empty signal mask, and `SIGPIPE` in the default set (what std
     does, so the reader starts like any `Command` child).
  3. `posix_spawn_file_actions_t`: `adddup2(stdin read end, 0)`, `adddup2(stdout write end, 1)`,
     `addopen(2, "/dev/null", O_WRONLY, 0)`, `posix_spawn_file_actions_addchdir_np(dir)`. With
     `POSIX_SPAWN_CLOEXEC_DEFAULT` only the targets of file actions survive the exec.
  4. `libc::posix_spawn` (never `posix_spawnp`), argv and envp as NUL-terminated `CString` arrays.
     A NUL inside any of them is `io::ErrorKind::InvalidInput`.
  5. Destroy the attr and the file actions on every path (a small guard type each). Drop the
     child-side ends after the spawn. Return the parent ends as `File`s.
- Every libc call's failure is an `io::Error` (`posix_spawn*` return the error number;
  `pipe`/`fcntl`/`waitpid` set errno). No `unwrap` or `expect` outside tests.
- `ExitStatus` from the raw wait status with `std::os::unix::process::ExitStatusExt::from_raw`.
- Not macOS: `spawn` returns `io::Error::new(io::ErrorKind::Unsupported, ..)`; the type and its
  methods still compile.
- Each `unsafe` block gets a one-line `// SAFETY:` comment, as `builder/agent/src/child.rs` does.

`Drop` is what makes a panic safe: a panic anywhere between the spawn and the wait unwinds through
it, and the reader is killed and reaped.

## 2. `Reader::spawn`

In `builder/agent/src/reader.rs`, move the argv and environment `command()` builds into one private
`fn launch(&self, args: &[&str]) -> (Vec<OsString>, Vec<(OsString, OsString)>)` (argv after
`sandbox-exec`, then the environment), and build both from it:

- `pub fn command(&self, args) -> Command` keeps its behaviour exactly (the profile tests use it,
  and the control in § 5 needs the old spawn).
- New `pub fn spawn(&self, args: &[&str]) -> io::Result<spawn::Spawned>`:
  `spawn::spawn(Path::new(sandbox::SANDBOX_EXEC), &argv, &env, &self.run)`.

The same `-p` profile, the same `-D` parameters in the same order, the same program and args, the
same environment built from nothing, the same working folder. A test (in § 5's file) asserts
`launch`'s argv and env equal what `command()` carries (`Command::get_args`, `get_envs`,
`get_current_dir`), so the two can't drift.

## 3. `reader_client::run` uses it, and a seam with deadlines

In `builder/api/src/reader_client.rs`:

- `run` calls `reader.spawn(&["reader", step.name()])` (an error is `STOPPED`, as today), then
  `supervise(child, &bytes, step, progress, QUIET, AFTER)`.
- New private `fn supervise<T: DeserializeOwned>(mut child: Spawned, request: &[u8], step: Step,
  progress: &mut dyn FnMut(ReadProgress), quiet: Duration, after: Duration) -> Result<T>`: what
  `run` does today after the spawn, moved unchanged: write the request to the taken stdin and drop
  it; judge the taken stdout with `judge_with_deadlines(.., quiet, after, || { let _ = child.kill(); })`
  (no stdout: kill and `STOPPED`); `wait_for_exit(&mut child, after)`; `finish`.
- `wait_for_exit` takes `&mut Spawned` instead of `&mut std::process::Child`; its body is
  otherwise unchanged.
- `Reader` must outlive the child (its `Drop` removes the run folder): keep `reader` alive in `run`
  until `supervise` returns, as today.

## 7. Fix: measure the reader's descriptors by identity, not by number

§ 5 test 1 fails under the real `sandbox-exec`: the reader started by `Reader::spawn` lists
`0 1 2 3 4 5`, not `0 1 2 3`. V1 measured why (2026-11-02), and none of it is the app's:

- `/bin/ls` opens two descriptors of its own (the folder and `.`): run with only 0 to 2 and no
  sandbox, it lists `0 1 2 3 4`.
- Under the reader profile the program also holds a connected Unix socket it opens itself at
  start: the system log socket, which `system.sb` lets every sandboxed program reach
  (`(allow network-outbound (literal "/private/var/run/syslog"))`). It is there with
  `Reader::command` too, with the environment emptied, and with the program `/bin/zsh`; the test
  process held only fds 0 to 2 when it appeared.

So a fixed list of numbers can't say "nothing came from the app". Change only
`the_reader_gets_only_stdin_stdout_and_stderr` in `builder/agent/tests/reader_spawn.rs`:

1. Keep the sibling `/bin/cat` and the fd 200 stand-in as they are.
2. In the test process, after setting those up, collect the identity `(st_dev, st_ino)` of every
   open descriptor 3 to 255 that is a pipe or a socket (`libc::fstat`; `S_IFIFO` or `S_IFSOCK` in
   `st_mode & S_IFMT`; skip `EBADF`). Call this `app`. Assert it holds fd 200's identity.
3. The measurement program is `/bin/zsh` (a real binary that starts nothing else; `/bin/sh` is a
   shim that runs another program, which the profile refuses), args
   `["-fc", "zmodload zsh/stat; for n in {3..255}; do [[ -e /dev/fd/$n ]] || continue; zstat -A d +device /dev/fd/$n; zstat -A i +inode /dev/fd/$n; print $n $d $i; done"]`
   (no `$(...)`: a subshell needs a fork). Each output line is `<fd> <device> <inode>`; parse it
   into `(fd, (dev, ino))`.
4. The control, `reader.command(..).output()`: some line has fd 200 and fd 200's identity in
   `app`. This proves the measurement sees an inherited descriptor.
5. `reader.spawn(..)` (drop stdin, read stdout to the end, `wait` succeeds): no line's identity is
   in `app`, and no line is fd 200.
6. If zsh prints nothing or `zmodload` is refused under the profile, stop and report it; do not
   change the profile.

Device and inode are plain numbers, never a path; print the parsed lines in the assertion message.
No other change.

## 8. Fix: the app measures through `/dev/fd` too

§ 7's control fails: zsh sees fd 200, but under another identity than the app's. On macOS,
`fstat` of a pipe gives device 0 and a 64-bit id, while `stat` of `/dev/fd/<n>` (what `zstat`
does) gives the devfs device and a 32-bit id (V1 measured both on one pipe, 2026-11-02). In the
test's loop over 3 to 255, replace `libc::fstat` with `std::fs::metadata(format!("/dev/fd/{fd}"))`:
skip an fd whose metadata fails with `NotFound` or raw `EBADF`, panic on any other error; keep
only `file_type().is_fifo()` or `is_socket()` (`std::os::unix::fs::FileTypeExt`); the identity is
`(MetadataExt::dev(), MetadataExt::ino())`. Drop the `MaybeUninit`/`unsafe` block that goes with
it. No other change.

## 9. The security review's and the Verifier's should-fixes

Both passed `7160e46`. Each item below is a gap in a test, or a hardening, on something that holds
today. Make exactly these; nothing else.

1. **`launch` returns the folder too.** `Reader::launch` returns `(argv, env, &Path)` with
   `&self.run` as the third; `command()` and `spawn()` both take the folder from it. (Today
   `spawn` names `&self.run` itself, and a change there passes every test.)
2. **The drift test runs both paths.** Replace `the_reader_spawn_matches_its_command` in
   `reader.rs` with a test in `builder/agent/tests/reader_spawn.rs`,
   `spawn_and_command_start_the_same_reader` (sandbox; `available()` first): one reader with

   run it through `reader.command(..).output()` and through `reader.spawn(..)` (drop stdin, read
   stdout to the end, `wait` succeeds); both succeed, and the two outputs are equal, compared with
   `assert!(a == b, "the outputs differ")` so no environment value is printed. Also assert the
   first line of the spawn's output is `reader.run_folder()` (as a `str`).
3. **The parent's ends are close-on-exec.** In `a_spawned_child_reads_stdin_and_writes_stdout`,

5. **A child reaped elsewhere.** In `Spawned::wait_with`, when `waitpid` fails with `ECHILD`, set
