## The problem

Every app command that spends (build, the interview draft, the refresh draft and its test) opens the
ledger with `Cap::default()`: $50 a day and $5 a step, fixed. The person can't change it in the app,
and the CLI's `--daily-cap-usd`/`--call-cap-usd` flags are forgotten after each run. The Connect
Claude mock (*How much it may use*) lets the person set both. This slice builds the dollar limit only;
the share-of-plan choice is PB7.7d (parked). Build no radio choice and no percentage field.

## Decisions (made, do not reopen)

1. **Where the limit lives.** `~/.claude/state/<slug>/limit.json`, written with `write_private`
   (0600, atomic), as `{"daily_usd": <f64>, "call_usd": <f64>}`. No file means the defaults.
2. **In `builder/agent/src/ledger.rs`:**
   - `pub const LIMIT: &str = "limit.json";`
   - `impl Cap { pub fn load(home: &Path, slug: &str) -> Result<Cap> }`: `read_private_optional`;
     `None` → `Cap::default()`; otherwise parse with serde into a private
     `#[serde(deny_unknown_fields)] struct Saved { daily_usd: f64, call_usd: f64 }` and pass both to
     `Cap::new`. A file that isn't that JSON, or whose values `Cap::new` refuses, is
     `Error::Invalid(text::limit_damaged(&path))`, so nothing spends (as a damaged ledger stops all
     spending). `load` never creates the state folder (`read_private_optional` doesn't).
   - `impl Cap { pub fn save(&self, home: &Path, slug: &str) -> Result<()> }`: writes the JSON with
     `write_private`. It takes no lock itself; callers hold the state lock.
   - `Cap::new`'s bounds stay as they are (0 < step ≤ day ≤ $1000, finite).
3. **`builder/agent/src/text.rs`:** `pub fn limit_damaged(path: &Path) -> String`:
   `"The daily limit saved at {path} can't be read, so Persona Builder won't spend anything. Set it again with `persona-builder limit set`, or on Connect Claude in the app."`
4. **The app's commands spend at the saved limit.** In `builder/api/src/building.rs`:
   - `pub(crate) fn open(home, slug)` loads `Cap::load(home, slug)` first (failure →
     `failure(LIMIT_DAMAGED)`), then `Session::open(home, slug, cap)` as today. Loading before the
     lock is fine: a limit saved while a session runs applies to the next one.
   - The two `last_spend` seeds (`building.rs` `build_assistant_in`, `review.rs` `apply_refresh_in`)
     use `session.cap().daily_usd()`, never `Cap::default()`. No `Cap::default()` is left in
     `builder/api/src/` outside tests.
   - Consts, in `building.rs` beside the others:
     - `LIMIT_DAMAGED`: "Persona Builder can't read the daily limit saved for this assistant, so it won't spend anything. Set the limit again on Connect Claude."
     - `LIMIT_BAD`: "The daily limit must be more than $0 and at most $1,000. The most one step may use must be more than $0 and no more than the daily limit."
     - `LIMIT_SAVE`: "Persona Builder couldn't save the limit. Check there's space on this computer, then try again."
5. **Two new app commands**, wired exactly as `spend_today` is (api fn + `_in` fn, Tauri command,
   `main.rs` handler list, `command_names.rs`, the autogenerated permission toml (let the build
   generate it, then commit it), the capability, `lockdown.rs`'s list, `parity.rs`, `backend.ts`,
   `tauri-backend.ts` and its test table, `test-support.ts`'s fake):
   - DTOs in `dto.rs` with the same derives and serde attributes as `Spend`/`SlugRequest`
     (camelCase, `deny_unknown_fields` on the request, `#[ts(export)]`; regenerate the TS types):
     - `pub struct SpendingLimit { pub daily_usd: f64, pub call_usd: f64 }`
     - `pub struct SpendingLimitRequest { pub slug: String, pub daily_usd: f64, pub call_usd: f64 }`
   - `spending_limit(SlugRequest) -> SpendingLimit`: `readable(home, slug)?` (it checks the
     assistant and permission), then `Cap::load` (error → `LIMIT_DAMAGED`). Takes no lock, writes
     nothing.
   - `set_spending_limit(SpendingLimitRequest) -> SpendingLimit`, in this order:
     1. `readable(home, slug)?`;
     2. `Cap::new(daily_usd, call_usd)` → on error `failure(LIMIT_BAD)` (nothing is locked or written);
     3. `private::lock_existing_state(home, slug)`: `NotFound`-style failure (the folder is gone) →
        `PERMISSION`; `private::BUSY` → the api's `BUSY` (a build or a test is running for this
        assistant: the limit can't change mid-run); anything else → `LIMIT_SAVE`;
     4. re-check `crate::read_consent(home, slug).agreed` under the lock → else `PERMISSION`
        (a Forget between step 1 and 3);
     5. `cap.save(home, slug)` → error `LIMIT_SAVE`; answer the saved values.
     Follow how `keep_answer_in` (review.rs) and its test
     `keep_refuses_forgetting_between_check_and_lock_without_recreating_state` handle steps 3–4, and
     match that error mapping.
   - `parity.rs`: `spending_limit` → `[["limit", "show"]]`, `set_spending_limit` → `[["limit", "set"]]`.
6. **The CLI.**
   - A new subcommand group `persona-builder limit`:
     - `limit show <member_dir>`: prints `text::limit(cap)`, a new agent text fn:
       `"Daily limit: about ${day:.2} a day, and at most ${step:.2} for one step, as Claude Code estimates it."`
     - `limit set <member_dir> --daily-usd <f64> --step-usd <f64>` (both required): `Cap::new`, then
       `lock_existing_state` (state folder missing → the CLI's existing "no permission/state" error
       path, whichever the CLI uses today for `lock_existing_state`; busy → `private::BUSY`), then
       `save`, then prints `text::limit(cap)`. Use `checked_member`/`member_and_home` as the other
       commands do.
   - Every CLI command that takes `--daily-cap-usd`/`--call-cap-usd` (`build`, `spend`,
     `refresh propose`, `refresh apply`, `interview draft`) changes them to `Option<f64>` with no
     `default_value_t`, help text gaining "(default: the limit set for this assistant, else $50)"
     / "(… else $5)". A new helper `fn cap_for(home, slug, daily: Option<f64>, call: Option<f64>) -> Result<Cap>`:
     `let saved = Cap::load(home, slug)?;` then `Cap::new(daily.unwrap_or(saved.daily_usd()),
     call.unwrap_or(saved.call_usd()).min(daily.unwrap_or(saved.daily_usd())))`. Note the `.min`
     only when `call` is `None` (an explicit `--call-cap-usd` above the day is still an error, as
     today). `spend` has no call flag: pass `None`.
7. **Connect Claude** (`ConnectClaude.vue`), the mock's second card, dollars only:
   - `PersonaBuilder.vue`: `<ConnectClaude v-else-if="view === 'connect' && assistant" :key="assistant.slug" :assistant="assistant" @next=…>`; the screen takes the `assistant` prop (type as the other screens do).
   - Keep the existing Claude card exactly as it is (PB7.7b owns its words). Below it, always (not
     only when Claude Code is ready), a second `<section class="card mt-3">`:
     - `<h2>` *How much it may use*.
     - Text: *The amounts are Claude Code's own estimates.*
     - Two fields side by side (`row g-3`, `col-md-6`), each a Tabler `input-group` with a `$`
       `input-group-text`, `inputmode="decimal"`, real `<label for>`s:
       *Stop for the day at about* (`id="limit-day"`) and *Most one step may use* (`id="limit-step"`),
       filled from `spendingLimit` on mount with `toFixed(2)`.
     - Text: *If the build reaches the limit, it carries on tomorrow. Persona Builder checks the limit before every step, so it stops before it goes over.*
     - A button *Save the limit* (`btn btn-primary`; the Claude card's *Next* stays the main action
       there). Disabled while loading or saving, and while both fields equal the loaded values.
     - Parsing in the screen: trim, drop one leading `$`, must match `^\d+(\.\d{1,2})?$`; else show
       *Enter an amount in dollars, like 50.00.* and send nothing. The bounds are the backend's
       (`LIMIT_BAD` comes back as the failure message).
     - On success: the fields take the answered values, and a line with `role="status"`:
       *Saved. Persona Builder stops for the day at about $X, and one step may use at most $Y.*
       On failure: `alert alert-danger` with `failureMessage(failure, LIMIT_SAVE's text)`.
       If `spendingLimit` fails on mount: the same alert, and the fields and button stay hidden.
   - No inline styles; Tabler classes only, as the rest of the app.
8. **Records.** `.ai/SECURITY.md`'s spending row: replace "at the default daily limit" with "at the
   daily limit set for that assistant (`limit.json` in its state folder, 0600, inside `Cap::new`'s
   bounds; a damaged file stops all spending; changed only under the state lock, so never mid-build)",
   and add `builder/agent/tests/cap.rs` already listed plus `builder/api/tests/building.rs`.
   `.ai/PROJECT.md`'s `builder/agent/` row: "the daily cap" → "the daily cap, set per assistant".

## Tests (write each red first)

  `save` then `load` round-trips (20.0, 2.5) and the file is mode 0600; `load` on `not json`, on
  `{"daily_usd": 2000, "call_usd": 5}`, on `{"daily_usd": 10, "call_usd": 20}`, on an extra field and
  on a missing field → the `limit_damaged` error.
- `builder/api/tests/building.rs`:
  - `spending_limit` → 50/5 with nothing saved; after `set_spending_limit(20, 2.5)` → 20/2.5.
  - `spend_today` after the set answers `dailyCapUsd` 20 (the build's *Today's use* line).
  - A build (with the existing stub Claude) after `set_spending_limit(1, 1)` and a ledger already
    holding $0.50 today is refused with `cap_reached(0.50, 1.00)`'s text: the saved limit is enforced.
  - `set_spending_limit` with (0, 0), (2000, 5), (10, 20), NaN → `LIMIT_BAD` and no `limit.json`.
  - `set_spending_limit` while a `Session` is open for the assistant → `BUSY`, file unchanged.
  - No permission → `PERMISSION` for both commands; a damaged `limit.json` → `spending_limit` and
    `spend_today` both answer `LIMIT_DAMAGED`; `set_spending_limit` then repairs it.
  - Forgotten between the check and the lock (as the `keep_answer` test does) → `PERMISSION`, and no
    state folder is recreated.
- `builder/cli/tests/agent.rs`: `limit show` prints the defaults; `limit set --daily-usd 20

- `ConnectClaude.test.ts`: the card shows 50.00 and 5.00 from `spendingLimit`; *Save the limit* is
