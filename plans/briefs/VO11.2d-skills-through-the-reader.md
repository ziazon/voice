# VO11.2d brief: the skills reading goes through the reader

VO11.2c made the app's history and claude.ai steps start the shipped `voice` as the reader, under
the profile, with exactly that step's sources (brief `plans/briefs/VO11.2c-app-reads-through-the-reader.md`).
The skills screen still reads in the app's own process: `builder/app/src/commands.rs` calls
`voice_api::list_skills`, `agree_skills`, `withdraw_skills` and `refresh_skills`, which call the
`_in` functions in `builder/api/src/skills.rs` directly, and a panel refreshes each seat's skills
copy (the mirror) in the app's process too (`refresh_mirrors` in `builder/panel-runner/src/run.rs`).
The reader already answers skills requests (`voice reader skills`, `voice_api::reader`, VO11.2b).
This slice makes the app use it, with the skill folders as the run's sources.

## Facts measured on this Mac (V1, 2026-11-02), which the design rests on

- Inside a Seatbelt profile, a path that **does not exist** gives `ENOENT` even where reading is not
  allowed; an **existing** folder that is not allowed gives `EPERM` ("Operation not permitted").
  So a skill root that doesn't exist needn't be a source: `discover` already treats `NotFound` as
  empty.
- `sandbox-exec` accepted 300 `-D` parameters with 300 `subpath` rules, and each still bit (a
  folder outside them was refused).
- People link skills in from elsewhere. One real setup has 48 of 49 folders in `~/.codex/skills`
  as symlinks into one other folder. `discover` canonicalizes each skill folder, so under the
  profile a link whose target isn't a source would silently drop that skill.
- Inside a skill folder, `skills/read.rs` never follows a link (`AT_SYMLINK_NOFOLLOW`; a link is
  `Source::Link`). Only the top-level skill folder, a synced account folder and the roots
  themselves are followed.

## 1. The skill folders, named once beside `discover`

`builder/ingest/src/skills.rs`:

1. Add `pub fn sources(home: &Path, rules: &Rules) -> Vec<(PathBuf, bool)>`: every place
   `discover(home, rules)` reads, as (path, is_folder), for the app to hand the reader. It reads
   only folder listings and link targets (never a file's contents) and never fails: anything it
   can't read is left out. In this order, each kept only when it exists (`fs::metadata` follows
   links; a missing one is skipped) and is of the stated kind:
   1. `~/.claude/skills` (folder).
   2. `~/.claude/plugins/installed_plugins.json` (file), then for each `(_, install)` that
      `plugin_roots(home)` returns (`Ok` only; on `Err` add nothing more for plugins),
      `install.join("skills")` (folder). Plugin skills that link outside their install are
      already skipped by `root_skills`, so no link targets here.
   3. For each `project` in `rules.projects()` not denied by `DenyList::builtin()`:
      `project.join(".claude/skills")` (folder).
   4. `~/.codex/skills` (folder).
   5. **Link targets.** For each root folder kept above **except** the plugin ones, and for
      `~/.claude/skills/synced/<account>` for each account folder (listed with `children`), take
      each child the way `discover` lists it (`children`, so hidden names are skipped). When the
      child's `symlink_metadata` says it is a link, `canonicalize` it; keep the target when it is a
      folder, not denied by `DenyList::builtin()`, and not already inside a kept path
      (`starts_with` one). Do the same for each synced account folder itself, before its children.
   Return the kept paths, de-duplicated, in that order.
2. A root folder the reader may not read: in `children` and `protect`, an error whose kind is
   `PermissionDenied` is now treated like `NotFound` **and** pushes `UNREADABLE_NOTE` onto the
   notes (once, as `add` does). `children` has no notes parameter today: add a
   `notes: &mut Vec<String>` parameter to both and thread it from `discover` and `root_skills`
   (`found.notes`). Every other error kind stays an error. This is also what a terminal run now
   says for a root folder it isn't allowed to read (it said `SKILLS_READ` before), which is the
   honest sentence.

## 2. The reader's source checks, shared with the caller

`builder/agent/src/reader.rs`:

1. `MAX_SOURCES` becomes 256 (measured above).
2. Move the per-source check inside `Reader::new` (the `if (if folder …) || canonical == "/" || …`
   block and the canonicalization before it) into a private
   `fn accepted(folder: bool, path: &Path, bounds: &Bounds, deny: &DenyList) -> Option<PathBuf>`
   returning the canonical path when the source is acceptable. `Bounds` is a private struct of the
   canonical home, member, state and runs that `Reader::new` computes today (move that code into
   `fn bounds(home, member, state, runs) -> Result<Bounds>`, same errors). `Reader::new` behaves
   exactly as before: a source `accepted` refuses is still `READER_SOURCE` for the whole run.
3. Add, beside `Reader::new` (macOS; off a Mac return an empty `Vec`):
   `pub fn usable<'a>(home: &Path, member: &Path, state: &Path, runs: &Path, sources: &[Source<'a>], deny: &DenyList) -> Vec<Source<'a>>`
   that returns the sources `Reader::new` would accept (same `bounds`, same `accepted`), in order,
   at most `MAX_SOURCES` of them (extra ones are dropped from the end), or an empty `Vec` when
   `bounds` fails. One derivation point: the caller filters with the reader's own rule, never a
   copy of it.

## 3. A refresh for a caller that already holds the lock

A panel holds every seat's state lock for the whole run (see the comment above `refresh_mirrors`),
so the reader's `refresh` would answer `BUSY`.

1. `builder/api/src/reader.rs`: `SkillsAction` gains `#[serde(rename = "refresh-held")] RefreshHeld`.
   `serve` refuses `ids` with it exactly as for `List` and `Refresh`, and answers it with
   `skills::refresh_held_in(home, slug)`.
2. `builder/api/src/skills.rs`: split `refresh_skills_in` into a private
   `fn refresh(home: &Path, member: &Member) -> Result<dto::SkillsRefreshed>` (today's body after
   the lock), `refresh_skills_in` (takes `locked`, then `refresh`), and
   `pub fn refresh_held_in(home: &Path, request: dto::SlugRequest) -> Result<dto::SkillsRefreshed>`
   (`listed(home, &request.slug)?` then `refresh`, no lock), with a doc comment: *for a caller that
   already holds this assistant's state lock (a running panel); anyone else uses
   `refresh_skills_in`.*
3. Docs (§ 7) say what this trusts: the request comes from the app or the person's own terminal.

## 4. The reader client's skills steps

`builder/api/src/reader_client.rs`:

1. Make the skills sentences `pub(crate)` in `skills.rs` (`SKILLS_READ`, `SKILLS_SAVE`, `GONE`,
   `NONE`, `REFRESH`, `REFRESH_STALE`, `REFRESH_REMOVED`) and add them, plus the `FIND` that
   `assistants::listed` returns if it isn't already the same text as `history::FIND`, to the list
   of sentences `Judge::line` passes through. `step_failure(Step::Skills)` is `SKILLS_READ`.
2. `fn skills_run<T: DeserializeOwned>(home, place, request: reader::SkillsStep) -> Result<T>`:
   find the assistant (`assistants::find`, `FIND` on any failure), its state folder
   (`member::private_state_dir`, `ELSEWHERE`), its `DenyList::for_member` and
   `Rules::for_member(&member.member, home)` (`SKILLS_READ` on failure), then
   `voice_ingest::skills::sources(home, &rules)` turned into `Source::Folder`/`Source::File`,
   filtered through `voice_agent::reader::usable(home, &member.dir, &state, place.runs, …, &deny)`,
   then `run(home, place, &request.slug, Step::Skills, &request, &usable, &mut |_| {})`.
3. Public, each building its `SkillsStep` and calling `skills_run`:
   `list_skills(home, place, SlugRequest) -> Result<Skills>`,
   `agree_skills(home, place, SkillsRequest) -> Result<Skills>`,
   `withdraw_skills(home, place, SkillsRequest) -> Result<SkillsWithdrawn>`,
   `refresh_skills(home, place, SlugRequest) -> Result<SkillsRefreshed>`,
   `refresh_held(home, place, SlugRequest) -> Result<SkillsRefreshed>`.

## 8. Tests

Name the seams: `voice_ingest::skills::sources` and `discover` (ingest unit tests);
`voice_agent::reader::usable` (`builder/agent/tests/reader_profile.rs`); the reader protocol
(`builder/api/src/reader.rs` tests); the app's path through the built `voice`
(`builder/cli/tests/reader_app.rs`, macOS, `available()` skip); the panel runner's injected
refresh (`builder/panel-runner` tests and `builder/api/tests/panels.rs`). No other seams.

1. **`sources` covers everything `discover` reads.** A home with: a plain skill in
   `~/.claude/skills`; one there that is a link to a folder in an invented `elsewhere/kit`; a
   synced account that is itself a link to `elsewhere/synced-a`, holding a skill; a plugin install
   under `~/.claude/plugins` with `installed_plugins.json` and a `skills/<name>`; a listed project
   whose `.claude/skills` holds a link to `elsewhere/project-skill`; `~/.codex/skills` with two
   links into one `elsewhere/codex` folder; a link whose target is under a `.ssh` folder.
   Assert the exact list (paths and kinds, in order), that the `.ssh` target is absent, and that
   every skill `discover` returns has its `folder` under one returned folder. A home with none of
   these returns an empty list.
2. **A root the reader may not read.** `chmod 000` a listed project's `.claude/skills` (restore
   it before asserting so cleanup works): `discover` returns the other skills and `UNREADABLE_NOTE`
   once; with mode restored, the note is gone.
3. **`usable`.** Same fixture style as `reader_profile.rs`: keeps an ordinary folder and file in
   order; drops a missing path, a folder given as a file and the reverse, home, a folder holding the
   state folder, a path inside the state or runs folder, a `.ssh` path, a path under one of the
   member's deny rules, duplicates; at most `MAX_SOURCES`; and `Reader::new` with exactly what
   `usable` returned succeeds. Update the existing too-many-sources test to the new constant.
4. **`refresh-held`.** In the reader protocol tests: while the test holds the state lock
   (`private::lock_state`), a `refresh` request answers `BUSY` and a `refresh-held` request answers
   a result; `refresh-held` with `ids` is `REQUEST`.
5. **Through the built `voice`** (`reader_app.rs`): with the fixture from test 1 (minus the
   plugin), `reader_client::list_skills` equals `list_skills_in` on the same home (the linked
   skills included); `agree_skills` then `refresh_skills` equal the `_in` answers and leave the
   same mirror files; `withdraw_skills` equals too; an unknown id answers `GONE`, empty ids `NONE`;
   `refresh_held` while the test holds the lock succeeds. A canary file in a folder that is not a
   source (a sibling of `elsewhere/kit`, linked from nowhere) never reaches the state folder
   (`no_canary_in`), and no run folder is left (the `Home` drop already checks both). A skill linked
   into a folder the member's deny rules name is not listed through the reader.
6. **The panel's refresh.** In the panel-runner tests: a refresher returning false sends one
   `SkillsNotRefreshed` per seat whose mirror is in use; returning true sends none; a seat whose
   mirror is not in use is never passed to it. `builder/api/tests/panels.rs`'s
   `convene_refreshes_agreed_skills_and_leaves_unused_mirror_absent` passes
   `refresh_mirror_here` and still passes.
