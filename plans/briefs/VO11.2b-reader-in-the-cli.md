# VO11.2b brief: the reader in the CLI

VO11.2 moves the app's *reading* (Claude Code history, a claude.ai export, skill folders) out of
the app's own process into the shipped `voice` command, run under a Seatbelt profile of its own.
VO11.2a built that profile (`builder/agent/sandbox/reader.sb`) and the launch library
(`voice_agent::reader::Reader`), unwired. **This slice, VO11.2b, gives `voice` a hidden
`voice reader <step>` mode that speaks a small JSON-lines protocol, makes the reading code work
under the profile, and makes the walks refuse hard-linked files.** It wires nothing into the app:
VO11.2c makes the app start the reader, VO11.2d moves the skills screens onto it.

## What V1 decided and measured (don't re-derive it)

- **Decided at VO11.2's pickup:** the reader is the shipped `voice` in a hidden mode; one request
  object on stdin, JSON lines out; hard links refused for files a reader finds *by walking a
  folder* (the Claude Code projects tree, a claude.ai export given as a folder, skill folders),
  never for a file the person chose directly (a claude.ai export file): a hard-linked file found by
  a walk is left out and counted where denied paths are counted today. The terminal CLI stays
  unsandboxed (it is the person's own).
- **Measured on Mimi, 2026-11-02 (macOS 27.0.1), under a profile like `reader.sb`:**
  - a descriptor walk from `/` opens the folders above an allowed path only with `O_SEARCH`
    (`O_RDONLY|O_DIRECTORY` is refused); outside any sandbox, an `O_SEARCH` folder descriptor
    works for `openat`, `mkdirat` and `flock`. `libc` 0.2.191 has `libc::O_SEARCH` on Apple
    (`O_EXEC | O_DIRECTORY`), not on Linux;
  - listing `~/.claude/crew` is refused (it is only a metadata-allowed folder above the member
    folder), so any lookup of an assistant that lists the crew folder fails inside the reader;
  - a folder that **doesn't exist** reads as "No such file or directory" inside the profile, but a
    folder that **exists and isn't a source** reads as "Operation not permitted". So skill
    discovery inside the reader works only when every existing skill root is a source (VO11.2d's
    job); your tests create only the roots they pass as sources.

## 1. Find one assistant without listing the crew folder

In `builder/core/src/assistants.rs` add, after `list`:

```rust
/// One assistant by its slug, read from its own folder: the same rule as `list`, without listing
/// the crew folder (Voice's reader may not).
pub fn find(home: &Path, slug: &str) -> Result<Option<Listed>> {
    let dir = assistant_dir(home, slug)?;
    match read_member(&dir.join("member.json")) {
        Ok(member) if member.slug == slug => Ok(Some(Listed { dir, member })),
        _ => Ok(None),
    }
}
```

Use it in `builder/api/src/assistants.rs` `listed()` and in `builder/api/src/history.rs`
`readable()` in place of `assistants::list(home)…find(…)`, keeping every other check and every
error sentence exactly as it is (`FIND` on `Err` and on `None`).

Tests (in `assistants.rs`'s `mod tests`): with a crew holding a valid assistant, one whose

## 3. Hard links are left out of the walks

A file "has another name" when `nlink() > 1` (`std::os::unix::fs::MetadataExt`, or `st_nlink`).
Check it from the metadata of the entry the walk found **and again** from the opened file
(`fstat`), since a link can appear between the two.

- **Claude Code history, `builder/ingest/src/mine.rs`.** In `session_files`, after the existing
  checks (deny list, name, link, not-a-file), an entry whose `entry.metadata()` (which doesn't
  follow links) has `nlink() > 1` adds 1 to `denied` and is skipped. `open_session` becomes
  `fn open_session(path: &Path) -> Result<Option<File>>`, returning `Ok(None)` when the opened
  file's `metadata()` has `nlink() > 1`; the mining loop adds 1 to `mined.denied` and skips that
  file. `folders()` gets the new count for free (it counts `session_files`). Keep the existing
  summary sentence; a linked file counts in the same `denied` number.
- **A claude.ai export given as a folder, `builder/ingest/src/claudeai.rs` `read_export`.** After
  `conversations.json` inside the folder is opened and its `metadata()` read, `nlink() > 1`
  returns `Err(invalid(format!("Voice won't read {}: the same file has another name somewhere
  else on this computer (a hard link). Make a copy of the export folder and choose the copy",
  inner.display())))`. An export **file** (the zip, or a `conversations.json` chosen directly) is
  read whatever its link count. The folder's file count stays as it is (it reads no content).
- **Skill folders, `builder/ingest/src/skills/read.rs` `walk`.** A new `Source::HardLink` in
  `builder/ingest/src/skills.rs`. A regular file whose `fstatat` `st_nlink > 1` becomes
  `Source::HardLink` without being opened; after the open, `metadata.nlink() > 1` also becomes
  `Source::HardLink` (no bytes kept). In `builder/ingest/src/anonymize.rs`, `Source::HardLink`
  maps to a new `LeftOut::HardLink`, whose `left_out_reason` is `"a hard link"`. Order the new
  variants after `Link` in both enums. Update every exhaustive `match`.

## 4. One strict JSON object, shared

Move the parsing core of `builder/cli/src/stdin_json.rs` (the `Fields` and `Object` types, the

```rust
pub enum ObjectError { Read(String), TooLarge, NotUtf8, Json(String) }
/// Read one JSON object, at most `limit` bytes, refusing duplicate and unknown keys as `T` does.
pub fn read_object<T: DeserializeOwned>(input: &mut dyn Read, limit: u64) -> Result<T, ObjectError>
```

to `--stdin needs UTF-8 text`. The existing `similar_stdin.rs` tests must pass unchanged.

## 5. The protocol: `builder/api/src/reader.rs` (new), `pub mod reader;` in `lib.rs`

Module doc: `//! The protocol of Voice's reader, the hidden \`voice reader <step>\`; see
docs/spikes/VO11-os-sandbox.md.`

```rust
pub const MAX_REQUEST: u64 = 64 * 1024;
pub const MAX_LINE: usize = 16 << 20;
pub const REQUEST: &str =
    "Voice's reader couldn't understand what it was asked to do. Close Voice and open it again.";
pub const TOO_MUCH: &str = "Voice found more here than it can show at once.";

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Step { ClaudeCodeFolders, ReadClaudeCode, ClaudeaiExportStatus, ListClaudeaiChats, ReadClaudeai, Skills }
impl Step {
    pub const ALL: [Step; 6] = [/* in the order above */];
    /// The word after `voice reader`.
    pub fn name(self) -> &'static str // "claude-code-folders", "read-claude-code",
        // "claudeai-export-status", "list-claudeai-chats", "read-claudeai", "skills"
}

#[derive(Clone, Copy, Debug, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum SkillsAction { List, Agree, Withdraw, Refresh }

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "camelCase", deny_unknown_fields)]
pub struct SkillsStep { pub slug: String, pub action: SkillsAction, #[serde(default)] pub ids: Vec<String> }

/// One line the reader prints: progress lines, then exactly one result or error line.
#[derive(Debug, PartialEq, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum Line<T> { Progress(ReadProgress), Result(T), Error(String) }

/// Answer one request: read it from `input`, do the step with the API's own checks, write JSON
/// lines to `output`. True when it ended with a result line.
pub fn serve(home: Option<&Path>, step: Step, input: &mut dyn Read, output: &mut dyn Write) -> bool
```

(Write `Step::ALL` and `name` out in full; the comments above only list them.) `serve` calls a
private `serve_with_limit(…, max_line: usize)` with `MAX_LINE`, so a unit test can use a small
limit. Each step's request and the existing `voice_api` function that does the work:

| Step | Request (`json_object::read_object`, `MAX_REQUEST`) | Work | Result `T` |
|---|---|---|---|
| `claude-code-folders` | `SlugRequest` | `history::claude_code_folders_in` | `ClaudeCodeFolders` |
| `read-claude-code` | `ReadRequest` | `history::read_claude_code_in`, progress relayed | `ReadCounts` |
| `claudeai-export-status` | `SlugRequest` | `history::claudeai_export_status_in` | `Option<ExportStatus>` |
| `list-claudeai-chats` | `SlugRequest` | `history::list_claudeai_chats_in` | `ChatList` |
| `read-claudeai` | `SlugRequest` | `history::read_claudeai_in`, progress relayed | `ClaudeaiCounts` |
| `skills` | `SkillsStep` | `list` → `skills::list_skills_in`; `agree` → `agree_skills_in`; `withdraw` → `withdraw_skills_in` (each with a `SkillsRequest { slug, ids }`); `refresh` → `refresh_skills_in` | `Skills`, `Skills`, `SkillsWithdrawn`, `SkillsRefreshed` |

Rules:

- `home` `None` (no `HOME`) writes `Line::Error(history::FIND)`.
- Any request failure (read error, over `MAX_REQUEST`, not UTF-8, not exactly one object, an
  unknown or repeated key, a wrong type, and `ids` given non-empty for `list` or `refresh`) writes
  `Line::Error(REQUEST)`: never serde's text, never the request's text.
- A `Failure` from the work writes `Line::Error(failure.message)`.
- Each line is one compact JSON object followed by `\n`, flushed. Progress lines are written as the
  API's progress callback gives them. A line over `max_line` bytes (newline excluded) is never
  written: a progress line over it is dropped, a result line over it becomes
  `Line::Error(TOO_MUCH)`.
- After a write fails (the app went away), write nothing more, finish the work, return `false`.
- Exactly one result or error line, always the last line. Nothing goes to stderr.

Unit tests in `reader.rs`'s `mod tests` (an invented home made with `new_assistant_in` and
`agree_consent_in`, as `history.rs`'s tests do, plus an invented `~/.claude/projects` session —
copy the shape of an existing fixture in `builder/api/tests/history.rs`): `read-claude-code` gives
progress lines then one `result` equal to a direct `read_claude_code_in` call's; no permission
gives one `error` line with `history::PERMISSION`; each request failure listed above gives exactly
one `error` line with `REQUEST`; `home` `None` gives `FIND`; a result over a small `max_line`
gives `TOO_MUCH`; a writer that fails after its first line gets nothing more and `serve` returns
`false`.
